## Ranked findings

### 1. `mex_operations.rs`: 79% of it (8,500 lines, 747 serde structs) is never referenced

**Evidence.** 143 `pub mod` operations, 947 `pub struct`s, each with `#[derive(Debug, Clone, Default, Serialize, Deserialize)]` (`wacore/src/iq/mex_operations.rs:1-60`). Workspace + bridge reference 23 modules (script over every `mex_operations::<mod>` / `use … mex_operations::{…}` in `src/features/{mex,newsletter,business,community,groups}.rs`, `wacore/src/iq/mex.rs`, `whatsapp-rust-bridge/src/wasm_client/connection.rs`). Those 23 modules are 2,212 of 10,738 module lines and 200 of 947 structs. The emitter (`tools/whatspec-codegen/src/emit/mex.rs:34`) walks `ir.operations` unfiltered — no `WANTED`, unlike `emit/enums.rs:106` and `emit/iq_targets.rs:64`.

**Why it matters.** Every one of those 747 unused structs gets two serde derive expansions plus `Debug`/`Clone`/`Default`, type-checked and MIR-built on every wacore compile (rustc does not skip unused generic impls until codegen). It is also the single biggest source of diff noise on a whatspec bump, and `rustdoc`/rust-analyzer index all of it.

**Change.** Add a `WANTED: &[&str]` of operation names to `emit/mex.rs` (same pattern as the enum emitter, same "binding" doc), emit only those. Keep a `--all-mex` flag or a `committed_artifacts` test that fails when a `WANTED` entry disappears from the bundle, so an operation the bundle drops is noticed. Adding an operation later is a one-line `WANTED` edit + regen, which is exactly how enums already work.

**LOC:** −8,500 in the generated file, +~40 in the emitter. **Risk:** low (nothing referenced changes). **Behaviour-preserving:** yes. Measure with `cargo build --timings -p wacore` before/after; expect a visible drop in wacore's front-end time.

### 2. `abprops.rs`: 2,664 constants, 16 read in production

**Evidence.** `props::WATCHED` (`wacore/src/iq/props.rs:68-84`) lists 16 `abprops::web::*` constants; every production read (`src/client/lid_pn.rs`, `src/retry.rs`, `src/client/app_state.rs`, `src/send/tctoken_lifecycle.rs`, `src/spam_report.rs`) is one of those. `abprops::ALL` and the per-module `ALL` slices are referenced only by `tests/ab_prop_watch_coverage.rs:69`, whose stated purpose is to check that every `web::FOO` read in `src/` also appears in `WATCHED`. `props::stale` (`props.rs:45-60`) already shows the hand-written form for flags the bundle no longer ships.

**Why it matters.** Compile cost is low (consts are lazy), but 18.7k lines is 11% of the crate, it dominates every whatspec bump diff, and the flag codes it carries are the one piece of the registry that rotates.

**Change.** Two options, in order of preference:
1. Emit a `WANTED` subset (the codegen already knows `WATCHED` lives in `props.rs`; simplest is to have the emitter take the list from a `wanted_abprops.txt` next to the enum `WANTED`). Move the coverage test into `tools/whatspec-codegen/tests/` where the full IR is available, so it still proves "every read is watched" without the crate carrying the registry.
2. If (1) is unpalatable, keep `ALL` but emit it behind `#[cfg(any(test, feature = "abprops-registry"))]` and enable that feature only from the `tests/` crate.

**LOC:** −18,500. **Risk:** low. **Behaviour-preserving:** yes (production reads are unchanged; `AbPropsCache` stores by code).

### 3. Three Signal store trait families for the same data

**Evidence.**
- (a) `wacore::store::traits::SignalStore` (`wacore/src/store/traits.rs:543-676`, 24 methods, bytes in/out) — the backend contract implemented by `InMemoryBackend`, `SqliteStore`, `JsBackend`.
- (b) `wacore_libsignal::protocol::storage::{SessionStore, IdentityKeyStore, PreKeyStore, SignedPreKeyStore, SenderKeyStore}` (`wacore/libsignal/src/protocol/storage/traits.rs:118-551`) — what the ciphers call.
- (c) `wacore_libsignal::store::{PreKeyStore, SignedPreKeyStore, SessionStore}` (`wacore/libsignal/src/store/mod.rs:13-58`) — a *third* family with the same names, returning raw `PreKeyRecordStructure`/`SessionRecord` and `Box<dyn Error>`, plus methods nothing needs (`get_sub_device_sessions` returns `Vec::new()` at `src/store/signal.rs:428`; `contains_prekey`, `load_signed_prekeys`, `delete_all_sessions`).

The runtime chain is cipher → (b) `SessionAdapter`/`PreKeyAdapter` (`src/store/signal_adapter.rs:128,414`) → (c) `impl … for Device` (`src/store/signal.rs:276-490`, plus a `macro_rules!` that re-implements (c) for two wrapper types at `signal.rs:34-210`) → `SignalStoreCache` → (a) backend. Family (c) is pure glue: `signal.rs` + `signal_adapter.rs` are 1,907 lines to move bytes between (b) and (a).

**Change.** Delete family (c). Have the (b) adapters call `SignalStoreCache` / (a) directly (the cache already speaks `ProtocolAddress` and typed records: `signal_cache.rs:1094-1300`). `record_helpers.rs` (440 lines) stays — it is the proto↔record bridge and is used by `src/prekeys.rs`, `features/rotate_key.rs`.

**LOC:** −58 in wacore, roughly −600 to −900 in `src/store/` (the other agent's scope, but the trait lives here). **Risk:** medium — this is the durability path; the review checklist in `agent_docs/signal_durability.md` applies. **Behaviour-preserving:** yes if done as a straight inlining.

### 4. `ProtocolNode` derive cannot express children, so the richest nodes are hand-written

**Evidence.** The derive handles attributes only (`wacore/derive/src/lib.rs:449-525`: `name`, `default`, `jid`, `string_enum`, `u64`, `u32`, `optional`). Result: `wacore/src/iq/groups.rs` has 1 derive and 6 hand `impl ProtocolNode`; `GroupInfoResponse` alone is 56 fields (`groups.rs:725-836`), a 235-line `into_node` (`836-1070`) and a 290-line `try_from_node_ref` (`1070-1359`). Inside those, the same two shapes repeat: 24× `node.get_optional_child_by_tag(&["x"]).is_some()` ↔ 16× `if self.x { children.push(NodeBuilder::new("x").build()) }` (flag children), and "child with a `value`/`type` attr" (`appeal_status`, `evolution_version`, `growth_locked`, `limit_sharing_enabled`). `GroupParticipantResponse` (`628-682`), `GroupEphemeralSettings` (`690-722`), `ParticipantChangeResponse` (`1700-1790`), `stanza/groups.rs::parse_action` (`477-702`), `stanza/call.rs::parse_action` (`258-454`) are the same story.

**Change.** Extend the derive with three field kinds, all of which the existing `node.rs` helpers already implement at runtime:
- `#[child(tag = "locked", flag)]` on `bool` → presence child;
- `#[child(tag = "member_add_mode", text, string_enum)]` on `Option<E>` → text-content child;
- `#[children(tag = "participant")]` on `Vec<T: ProtocolNode>` → `collect_children`.
That covers ~80% of `GroupInfoResponse`; the remaining bespoke bits (`description` subtree, `id` fallback) stay in a small hand-written `try_from_node_ref` override or a post-hook.

**LOC:** −350 to −450 in `groups.rs`, −150 in `stanza/groups.rs`, plus future nodes cost a struct instead of two functions. **Risk:** medium (round-trip tests in `groups.rs:3678+` are thorough and should be kept as the oracle). **Behaviour-preserving:** yes.

### 5. `wacore-binary`: `Node` / `NodeRef` / `OwnedNodeRef` triplicate the read API; `AttrParser` / `AttrParserRef` duplicate 200 lines

**Evidence.**
- `attrs.rs:30-200` (`AttrParserRef`) and `attrs.rs:204-439` (`AttrParser`) are the same 20 methods (`optional_string`, `required_jid`, `optional_u64`, `unix_time`, …) over `&[(NodeStr, ValueRef)]` vs `&Attrs`. Only `get_raw` differs.
- `node.rs:700-745` (`Node`) and `node.rs:775-850` (`NodeRef`) re-implement `get_optional_child`, `get_optional_child_by_tag`, `get_children_by_tag`, `content_as_string`; `node.rs:969-1036` (`OwnedNodeRef`) forwards all 12 of them again by hand although `get()` already returns `&NodeRef`.
- `encoder.rs:476-535`: `node_encoded_size_with_cache` and `node_ref_encoded_size_with_cache` are identical modulo type. `marshal.rs:46-300`: every entry point (`marshal`, `marshal_to`, `marshal_to_vec`, `marshal_auto`, `marshal_exact`, `should_auto_reserve_node`, `estimate_capacity_node`) exists twice. The `EncodeNode` trait (`encoder.rs:100-190`) already abstracts the two for encoding but is not used for sizing or marshalling.

**Change.** (i) Make `AttrParser` generic over a tiny `AttrSource` trait (`fn lookup(&self, key) -> Option<Cow<str>>; fn lookup_jid(...)`), one impl each. (ii) Add `fn children(&self) -> Option<&[Self]>` + `tag()` to a `NodeLike` trait and write the four child-lookup helpers once. (iii) Move sizing/auto-reserve/capacity-estimate onto `EncodeNode` and collapse the `marshal_*` / `marshal_ref_*` pairs into one generic set (keep the public names as thin aliases if the bridge uses them). (iv) `impl Deref<Target = NodeRef<'_>> for OwnedNodeRef` is *not* possible (self-referential lifetime), so keep the forwarders but generate them with a `macro_rules!`.

**LOC:** −200 (attrs) −60 (node) −60 (encoder) −150 (marshal) ≈ −470. **Risk:** low; the marshal tests (`marshal.rs:478-720`) already assert `Node`/`NodeRef` byte-equality. **Behaviour-preserving:** yes. Perf: neutral; monomorphisation keeps the same code.

### 6. In-file test mocks re-implement the libsignal store traits 51 times

**Evidence.** `wacore/src/send/tests.rs` has 21 `impl {Session,IdentityKey,PreKey,SignedPreKey,SenderKey}Store for …` blocks across five clusters (`:1259-1330`, `:3184-3410`, `:4903-5000`, `:6178-6230`, `:6426-6520`) — `MemSessionStore` is defined three times, `UnusedPreKeyStore` twice, `MemSenderKeyStore` three times. Each of `wacore/libsignal/tests/{session_divergence,counter_lease,legacy_session_skipped_keys,crypto_provider_x25519_agreement,crypto_provider_agreement_failure}.rs` opens with the same ~105-line `InMemory{IdentityKey,PreKey,SignedPreKey,Session}Store` block (`session_divergence.rs:25-130`). `wacore/libsignal/benches/libsignal_benchmark.rs:58-260` and `wacore/benches/send_receive_benchmark.rs:172-290` have them a seventh and eighth time. Upstream libsignal ships `InMemSignalProtocolStore`; this fork removed it and re-created it per file.

**Change.** Add `wacore_libsignal::test_util::InMemProtocolStore` (all five traits, `Arc<Mutex<…>>` inside so it is `Clone`), gated `#[cfg(any(test, feature = "test-util"))]` — wacore already has that feature convention (`wacore/Cargo.toml` `test-util`). The `Unused*` and `Failing*` variants become two tiny wrappers.

**LOC:** −1,200 to −1,400. **Risk:** none for production. **Behaviour-preserving:** yes.

### 7. `SignalStoreCache`: 6 locks, 5 atomics, a bespoke "was I raced" protocol, and a 190-line flush written three times

**Evidence.** `signal_cache.rs:420-446`: `sessions`, `identities`, `sender_keys`, `removed_prekeys`, `sender_key_locks` (async mutexes), `pending_session_restores` (sync mutex), plus `session_wire_gate`, `sender_key_wire_gate`, `has_pending_session_restores`, `has_pending_sender_key_distributions`, `session_recovery_generation`. `UserIndexedCache` (`:229-247`) carries `removal_seq`, `recent_removals: VecDeque<(u64, Arc<str>)>` and `opaque_removal_seq` solely so `checkout_session` (`:1108-1180`) can drop the lock around backend I/O and then decide whether the slot was evicted in between (`UNLOCKED_COLD_READ_ATTEMPTS = 2`, then a locked retry). `flush` (`:1695-1888`) is the sessions block, then the identities block, then the sender-keys block — same shape (collect dirty/deleted → batch put → per-key delete → clear dirty → evict) with only the serializer differing.

**Simpler design.** Replace the removal-sequence machinery with a per-key *loading placeholder* (single-flight): insert `SessionEntry::Loading(Arc<Notify>)` under the lock before the backend read, so a concurrent eviction/clear cannot make the slot ambiguous and a second cold reader waits instead of re-reading. That removes `removal_seq`, `recent_removals`, `opaque_removal_seq`, `removed_since`, the retry loop, and the `cold_read_race_tests` module (`:5655-6224`) shrinks to one test. Independently, factor `flush` into `async fn flush_store<S: DirtyStore>(state: &Mutex<S>, backend, put_batch, delete)` — three ~15-line calls.

**LOC:** −120 (flush) −150 (removal tracking) −400 (its tests). **Risk:** high for the single-flight change (durability invariants in `agent_docs/signal_durability.md`; run the chaos matrix); low for the flush refactor. **Behaviour-preserving:** flush refactor yes; single-flight changes lock-hold semantics (still no backend await under the lock) — needs the review checklist.

Regardless of design: move the 4,126 test lines to `store/signal_cache/tests/*.rs` (they are already six named `mod`s at `:2101, :3551, :4267, :4433, :4884, :5655`). Zero risk, and the 2,100 production lines become readable.

### 8. `events.rs`: `EventKind`, `Event`, and `Event::kind()` are three hand-maintained copies of one list

**Evidence.** `wacore/src/types/events.rs:217-295` (`EventKind`, 78 variants), `:873-1130` (`Event`, 78 variants), `:1137-1215` (a 72-arm `match` mapping one to the other). `EventKind`'s discriminant is a persisted `EventInterest` bit index (`:312`), so the order is load-bearing — which is precisely why generating it from one source is safer than three parallel lists with a comment saying "keep in sync".

**Change.** One `define_events! { Connected(Connected), … }` macro that emits the `Event` enum (with the doc comments), the `EventKind` enum in the same order, `kind()`, and the `MAX_KINDS` guard. Payload structs stay as they are (the `bon::Builder` policy is untouched).

**LOC:** −90. **Risk:** low; add a test asserting `EventKind::X as u8` for a handful of pinned variants so a reorder fails CI. **Behaviour-preserving:** yes.

### 10. `history_sync.rs` carries two implementations of message-secret extraction

**Evidence.** A hand-rolled wire walker (`FieldIter` `:1328-1440`, `fast_extract` `:1441-1616`, `scan_message_level` `:1674-1750`, `unwrap_to_base`, `scan_context_info`, `carrier_slot`/`wrapper_slot` tables `:1252-1327`) that returns `FastExtract::Fallback` for "shapes prost merge semantics a single-pass walk cannot reproduce" (`:1220-1229`), and a full-decode path (`push_secret_record` `:2127-2185`, `base_message_view`, `message_is_forwarded_at_depth`, `first_wrapped_message`, `message_context_is_forwarded` `:2199-2348`) that re-derives the same five facts from a decoded `wa::Message`. Roughly 700 + 250 lines to compute `(from_me, msg_id, participant, secret, timestamp, is_poll_or_event, is_bot_invocation, is_forwarded)`.

**Change.** This is a deliberate performance design and the fallback is what makes it correct, so do not delete either blindly. But: (i) the decoded path's forwarded/wrapper logic duplicates `proto_helpers::MessageExt::{get_base_message, is_forwarded}` (`proto_helpers.rs:224-262, 503`) — use those; (ii) run `wacore/benches/history_sync_benchmark.rs` with the fast path forced to `Fallback`; if the gain is under ~2×, the walker should go. Either way the two must stay behaviourally identical, and there is no differential test asserting that today — add one (feed every fixture through both, compare).

**LOC:** −80 now, potentially −700. **Risk:** medium. **Behaviour-preserving:** yes for (i).

**LOC:** −250. **Risk:** low. **Behaviour-preserving:** yes.

### 12. Parsing helpers exist three times with subtly different semantics

**LOC:** −110. **Risk:** low. **Behaviour-preserving:** yes.

### 13. JID attribute round-trips: `optional_string` on a JID value formats then re-parses

**Change.** Use `optional_jid_result` where the target is a `Jid` (the `Jid::group(id)` fallback becomes `Jid::from_str` with the existing bare-id branch). Collapse the render helpers to `write_display_to` + one `push_*` over `impl fmt::Write`. **LOC:** −60. **Risk:** low. **Perf:** removes an allocation per JID attribute read on those paths.

### 15. `waproto`: 752 messages generated, ~140 named anywhere
