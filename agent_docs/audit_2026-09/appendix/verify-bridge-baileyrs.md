# Adversarial verification of the bridge / baileyrs audits

Method: for each report's top findings I read the cited code (symbols, not line numbers), the four documents the user named (`whatsapp-rust-bridge/AGENTS.md`, `baileyrs/README.md`, `baileyrs/src/Compatibility/README.md`, `baileyrs/ATTRIBUTION.md`), and, where a finding rests on upstream Baileys, the `baileys@7.0.0-rc13` tarball from the npm registry. No wasm builds were run. Paths are absolute; `core:` = `/home/user/whatsapp-rust`, `bridge:` = `/home/user/whatsapp-rust-bridge`, `baileyrs:` = `/home/user/baileyrs`.

Verdict key: **CONFIRMED** (fact and fix hold) · **OVERSTATED** (fact holds, number/impact does not; corrected estimate given) · **WRONG** (the fact does not hold) · **UNSAFE** (the proposed change breaks a documented contract, an upstream API shape, a persisted format, a wasm-bindgen constraint, or a semver promise).

Note first: both audits are already committed in-tree — `bridge:docs/architecture-audit-2026-09/` (commit b14f62b) and `baileyrs:audits/architecture-2026-09/` (commit 4aea0da). The numbers corrected below are therefore now in the repos' own docs.

## Missed by the reports

1. **Bridge ships a `.d.ts` that depends on a devDependency.** `ts/proto-reader.ts` subclasses `@bufbuild/protobuf/wire`, `ts/index.ts` re-exports `BinaryReader`, and `@bufbuild/protobuf` is only in `devDependencies` (`bridge:package.json:63-64`). `tests/published-dts.test.ts` passes only because the bridge repo has it installed. Every consumer has to add it themselves (baileyrs did — and the baileyrs audit then flagged it as unused). It belongs in `dependencies` or `peerDependencies`.
2. **The declaration audit is not a CI gate.** `baileyrs:.github/workflows/ci.yml` runs lint, tests, build/check-pack and e2e; no job runs `compat:audit:strict` (`package.json:63`); `test:compat-auditor` tests the tool, not the surface. The README says compatibility "is checked rather than assumed" — for exports it is checked manually. Given how many of the audits' suggestions are API-visible (reports 3 #8, #10), this is the gate that should exist before any of them land.
3. **`pair_success` is a live type/dispatch mismatch in the bridge.** `generated_types.rs:1136-1141` declares `id: Jid`, the hand-written union line (`wasm_client.rs:267`) says `string`, and the dispatch emits `to_string()` (`:2108-2118`). The generated `PairSuccess` interface is dead and wrong; baileyrs works around it (`schema.ts:158-163`). One-line fix, independent of any redesign.
4. **The spawn-throttle rationale is stale.** `bridge:src/runtime.rs:268-272` blames a core 1-permit semaphore that "wakes ALL waiters"; `async-lock 3.4.2` wakes one (`notify(1)` / `add_permits → notify(n)`). Report 1 #13 asks the core to fix a bug it did not verify.
5. **`Jid::Display` is lossy for `integrator`.** `write_jid!` has no integrator arm while `decoder.rs:214` reads it for interop JIDs and `is_same_chat_as` compares it. Any "JID as string" plan (report 3 #1, report 1 #2) collapses distinct interop chats into one string. Neither report checked the render path.
