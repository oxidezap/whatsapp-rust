## Ranked findings

### 1. `codegen/src/proto_gen.rs` (785 LOC) is a dead second proto-type generator

- **Evidence.** `codegen/Cargo.toml:11-13` declares bin `gen-proto-types = src/proto_gen.rs`. Nothing invokes it: `package.json:42` `gen:proto-types` runs `scripts/gen-protobufjs-dts.ts`, and grep over `.json/.yml/.md/.ts/.rs/.toml` finds no other reference. Its `find_waproto_source` (`proto_gen.rs:76-124`) only works with a sibling clone at `../../whatsapp-rust` or a git checkout — it cannot run against the registry layout `main.rs:41-66` supports — and `panic!`s otherwise. It has 0 tests (`main.rs` has 20). It emits a `_TS_PROTO_TYPES` custom section (`proto_gen.rs:766-767`) that would duplicate `proto-types.d.ts` if it were ever wired in. CI compiles and clippies it on every run (`ci.yml` "Codegen format, lints and unit tests" uses `--all-targets`).
- **Change.** Delete the file and the `[[bin]]` entry.
- **LOC:** −785 (+0). **Risk:** none. **Behaviour-preserving:** yes.

### 2. The shipped codec is ~12% larger than any consumer can use, and the namespace defeats every form of laziness the repo's own measurement recommends

- **Evidence (dead surface).** `fromPartial` (7,348 lines) and `create` (755 × 3 lines) are emitted for every message. Their only runtime callers are `ts/proto.ts:215-221` (`declaredFieldsOf`, a cold path reached after an encode already threw) and `ts/proto-namespace.ts:111` (re-exported as `fromPartial`). The published `.d.ts` never declares `fromPartial` (`gen-protobufjs-dts.ts:239-244` renders `create/fromObject/toObject/encode/decode/toJSON` only). baileyrs calls it only as an optional hook (`baileyrs/src/Compatibility/proto-runtime.ts:548` `sourceCodec.fromPartial ? … : message`) and never `.fromPartial(` directly (grep: 0 hits outside that file).
- **Evidence (no tree-shaking, no laziness).** `ts/proto.ts:79` and `ts/proto-namespace.ts:31` both `import * as gen` and `proto-namespace.ts:175` walks `Object.entries(gen)` at import, wrapping all 755 codecs eagerly. That makes every consumer pay for the whole schema whether it imports `encodeProto` alone or `proto`. `docs/proto-codec-memory.md:403-540` measured a per-type lazy namespace at −1.91 / −0.93 MiB private memory per process with **no API change**, listed the seven implementation pitfalls, and closed with "This is not implemented here." `benches/codec-memory/equivalence.mjs` (481 LOC) already exists to prove such a rewrite equivalent.
- **Which messages are actually used.** baileyrs decodes/encodes `Message` (37 sites), `WebMessageInfo` (7), `HistorySync` (4), `Config`, `PreKeyRecordStructure`, `MediaRetryNotification`, `ServerErrorReceipt`, `Message.PollVoteMessage`, `Message.EventResponseMessage`, `Message.AppStateSyncKeyFingerprint` — ~10 roots. But `proto` is a public namespace over all 657 types and `encodeProto("X")` resolves any name, so a cut is an API change (`docs/proto-codec-memory.md:544-575` says so correctly). Per-message splitting is not viable in a single-file bundle either.
- **Change.** (a) Add `outputPartialMethods=false` to `TS_PROTO_OPTIONS` (`gen-ts-proto.ts:205-211`); replace `declaredFieldsOf` with a direct walk of the normalized input (when two declared *and* undeclared keys carry the same bad code unit at the same index the path is already reported as ambiguous — losing the undeclared-key filter only widens that already-rare case). Drop the `fromPartial` line from `wrapMessage`. (b) Implement the lazy per-type namespace the doc recommends: `proto-namespace.ts:172-205` becomes descriptor-copying getters that self-replace on first read; turn `equivalence.mjs` into `tests/proto-namespace-lazy.test.ts`.
- **LOC:** (a) ≈ −9,600 generated, −12 hand-written; ~−110–130 KB minified (the codec is ~90% of the 1.09 MB bundle). (b) +~80 in `proto-namespace.ts`, −481 bench after conversion. **Risk:** (a) low; (b) medium — the nine accessor-vs-data-property corners in the doc are the whole observable difference. **Behaviour-preserving:** (a) yes for the declared surface (`fromPartial` was never in the `.d.ts`); (b) yes except the documented `Object.defineProperty`/`Reflect.set`-on-frozen corners.

### 3. `codegen/src/main.rs` is a second implementation of serde's (and `WireEnum`'s) data model, and it has already drifted

- **What it does that wasm-bindgen cannot.** The event payload types live in a crate the bridge does not own (`wacore`, `whatsapp-rust`), so the orphan rule blocks `#[derive(Tsify)]`; the generator scrapes those sources with `syn` and emits exactly what Tsify would — a `typescript_custom_section` (`main.rs:300-303`). So it is not redundant with `result_types.rs` (which covers bridge-owned types via Tsify, 80 derives) — but it *is* a second source of truth for serde semantics: `parse_source` `main.rs:644-1032` (390 lines) plus `parse_serde_container/serde_string_argument/has_serde_skip/apply_rename_rule/get_serde_rename/serde_container_shadow/serialize_with_type/timestamp_module_type` (`main.rs:1034-1490`) re-implement `rename_all`, `tag`/`content`, `untagged`, `skip`, `with`, `serialize_with`, `from`/`into`; `wire_enum_kind/get_wire_attr_lit/is_wire_fallback/has_wire_skip` (`main.rs:1177-1290`) re-implement the core's proc-macro by string-matching its attribute tokens; `rust_type_to_ts` (`main.rs:1493-1655`) hard-codes `SmallVec`, `CompactString`, `Arc`, `Box`, `DateTime`…
- **Drift, proven.** `main.rs:669-677` `TSIFY_STRUCTS` skips `BusinessProfile, BusinessCategory, BusinessHours, BusinessHoursConfig, GroupMetadataParticipant, MembershipRequest` "already generated by Tsify derives in result_types.rs". Only `GroupMetadataParticipant` still exists under that name (`src/result_types.rs:543`); the others were renamed to `BusinessProfileResult` (:811), `BusinessCategoryResult` (:827), `BusinessHoursConfigResult` (:847), `MembershipRequestResult` (:766). The core still declares the unsuffixed structs with `serde::Serialize` (`whatsapp-rust/wacore/src/iq/business.rs:65,81,90,131`, `groups.rs:3080`), so five core types are silently dropped from `generated_types.rs` for a conflict that no longer exists. `assert_declarations_are_closed` cannot see this because nothing references them.
- **Change.** Preferred (cross-repo, same org): add `ts-rs` behind a `ts` feature in `wacore`/`whatsapp-rust` (derive-only, no runtime, exports at `cargo test`; understands every serde attribute above natively; `#[ts(type = "…")]` covers the three `with` modules and `JsonValue`), have the bridge consume the exported `.ts` as its custom section, and delete the scraper. The CI drift check (`ci.yml` "Fail if the generated types drifted") and `tests/published-dts.test.ts` stay as the gate. Interim, in-repo: delete the stale skip list and derive the "names Tsify already declares" set from `src/result_types.rs` at generation time (one `syn` pass over one file the bridge owns), so the two sources can no longer disagree.
- **LOC:** preferred −2,355 (`main.rs`) −1,693 (`generated_types.rs`, becomes a copied `.ts`) +~60 attrs in the core. Interim −8/+15. **Risk:** preferred medium-high (needs a core release; output must be diffed once); interim none. **Behaviour-preserving:** interim yes; preferred yes for the emitted `.d.ts` by construction of the drift check.

### 4. Four independent text parsers of `whatsapp.ts`, while the descriptor is already in hand

- **Evidence.** `scripts/gen-protobufjs-dts.ts:37-98` parses the generated TypeScript with the compiler API and reverse-engineers field types from text (`translateType` `:145-160` splits on `_`, guesses enum-vs-message by a name set). `scripts/gen-ts-proto.ts:58-63,133-137,176-177` patches by regex. `scripts/proto-wire-type-guards.ts:80-102` is a hand line-parser. `benches/codec-memory/slice.ts` is a block parser. `tests/proto-field-boundaries.test.ts:367` reads the text too. Meanwhile `gen-ts-proto.ts:393-401` already writes a `FileDescriptorSet`, and it is walked *twice* with duplicated recursion: `buildSurface` (`gen-ts-proto.ts:288-375`) and `declaredTagsByCodec` (`proto-wire-type-guards.ts:58-77`) each define their own `local()`/`collect` over `file.messageType`/`nestedType`.
- **Change.** Emit `proto-types.d.ts` from the descriptor: one walk yields message path, fields (name, number, label, type, type-ref) and enum members — the surface manifest already carries everything but enum member names. Share that walk with `buildSurface` and `declaredTagsByCodec` (one `descriptorIndex(descriptor)` helper). The only thing the current generator gets from the *TypeScript* is the `Int64` retyping (`gen-ts-proto.ts:70-125`), which the descriptor knows directly (`Type.INT64|UINT64|SINT64|FIXED64|SFIXED64`). `typescript` then leaves the gen path.
- **LOC:** −~150 across the two scripts (delete the AST parse and `retypeInt64Fields`' first pass; keep the renderer). **Risk:** low — CI's drift check proves byte-identity. **Behaviour-preserving:** yes.

### 5. Namespace wrapper does per-message work the real consumer immediately throws away

- **Evidence.** `ts/proto-namespace.ts:73-79`: `encode` ignores the captured `fns` and calls `encodeProto(typeName, obj)`, which re-resolves by string every call (`ts/proto.ts:93-107`: `REGISTRY` miss → `typeName.replace(/\./g, "_")` → module lookup); `decode` (`:95`) uses `fns` directly — the two halves disagree. `decode` then `attachToJSONIdentity` (`:62-71`, an `Object.defineProperty` per decoded root). baileyrs's hot path (`baileyrs/src/Socket/events.ts:1180` `WAProto.Message.decode(reader, end - start)`) lands in `proto-runtime.ts:799-848`, whose `hydrate` copies the whole tree into fresh prototype-bearing instances precisely because "the codec installs its own `toJSON` on what it returns, and deleting that normalizes the object into dictionary mode". A no-op `toJSON` also changes nothing for `JSON.stringify`; it only prevents a throw on an explicit `.toJSON()` call.
- **Evidence (registry).** `ts/proto.ts:41-73` `REGISTRY` has 31 entries; 26 are byte-for-byte what the fallback lookup would return (verified against `whatsapp.ts` export names). Only the five non-generated spellings (`AdvSignedDeviceIdentity`, `AdvSignedKeyIndexList`, `AdvDeviceIdentity`, `AdvSignedDeviceIdentityHmac`, `LidMigrationMappingSyncPayload`) do anything — as `docs/proto-codec-memory.md:420` also notes.
- **Change.** Factor `encodeWith(fns, typeName, obj)` out of `encodeProto` and use it from `wrapMessage.encode`; memoize `resolve` in a `Map`; shrink `REGISTRY` to a 5-entry alias map. Move `toJSON` off the per-instance path: either drop it from `decode` (keep on `fromObject`) or expose the `into` parameter the merge patch already added to every `decode` (`gen-ts-proto.ts:127-129`) so a consumer decodes straight into its own prototype-bearing object and skips its top-level re-walk.
- **LOC:** −35. **Risk:** low. **Behaviour-preserving:** registry/memo yes; dropping `toJSON` from `decode` is not (an explicit `.toJSON()` on a decoded message would throw) — ship it as the `into` option first.

### 7. Build pipeline: five-command shell strings, tsc compiling 81k generated lines just to `rm -rf` the output, two lockfiles, orphaned scripts

Delete the orphaned `bench*` scripts. Keep one lockfile. Put `types` first.
- **LOC:** ~+40 / −6 fragments. **Risk:** low. **Behaviour-preserving:** yes.

### 9. `wire-info.ts`: two header/table readers, hand-mirrored Rust constants, and ~230 LOC of test-only encoders in the production bundle

### 10. Codec work is done three times per message across the boundary (inherent to "JS owns the object model", but one prost encode per inbound message is avoidable)

- **Evidence.** Inbound: core decodes with prost into `InboundMessage { message: Arc<wa::Message> }` (`whatsapp-rust/wacore/src/types/events.rs:1245-1248`) → bridge re-encodes every one (`src/wire_batch.rs:511` `message_encode_into`) → JS decodes again with ts-proto (`baileyrs/src/Socket/events.ts:1180`). History sync likewise: `src/wasm_client.rs:2047` `history_sync_to_vec` for JS to decode. Outbound: `encodeProto('Message')` → `waproto::codec::message_decode` (`src/wasm_client.rs:3525,3572`, `src/wasm_client/signal.rs:691`) → core re-encodes for Signal. These are not the *same* decode done twice — the core needs the struct, JS needs the object — but the inbound re-encode is pure transport cost and also loses byte fidelity (the JS side parses the bridge's re-serialization, not the peer's bytes, which matters for the parser-differential work the repo invests in: `tests/proto-field-boundaries.test.ts`, `proto-message-merge.test.ts`).
- **Change.** Have the core keep the decrypted plaintext (`InboundMessage { raw: Bytes }` or `Arc<[u8]>`) and cross those bytes; the bridge drops `message_encode_into` on that path. Cross-repo.
- **LOC:** −~20 bridge, +~15 core. **Risk:** medium (core event payload is a frozen API with `bon::Builder` — an added `Option` field is additive). **Behaviour-preserving:** bytes crossing may differ from today's re-encoding only where the peer's encoding was non-canonical, which is the point.

### 12. Dependencies and small inconsistencies

- `@bufbuild/protobuf` is a devDependency but a *runtime* dependency of the shipped bundle (`ts/proto-reader.ts:1-4` subclasses its `BinaryReader`/`BinaryWriter`; bun inlines it). Correct for a single-file bundle, but the generated decoders' `input instanceof BinaryReader` (every `decode` in `whatsapp.ts`) tests against the bridge's subclass, so a caller passing a stock `@bufbuild` reader gets it re-wrapped and its position is not advanced — worth one line in the `decode` doc.
- `ws` is imported by `tests/helpers.ts:5` and transitively by `examples/connect.ts:12` but is not declared in `package.json` (neither lockfile lists it); it only works because Bun ships a `ws` shim — `node` runs of the example fail on `MODULE_NOT_FOUND`.
- `typescript` is needed at gen time only by `gen-protobufjs-dts.ts` (goes away with #4) and by `tsc`/`published-dts.test.ts`.
- `pkg-pr-new` is used (`ci.yml:307`). `@types/node` + `@types/bun` are both needed (`bun-types` depends on `@types/node`). No unused packages found; the duplication is the two lockfiles (#7).
- Three separate `Adv*` alias tables for one compatibility concern: `ts/proto.ts:47-50,67` (runtime, `encodeProto` names), `ts/proto-namespace.ts:131-133` (`ADVKeyIndexList → ADVSignedKeyIndexList`, which never fires — `whatsapp.ts:8353` exports `ADVKeyIndexList` itself, as `docs/proto-codec-memory.md:424-427` notes), `scripts/gen-protobufjs-dts.ts:198-210` (11 *type-only* aliases: `export type AdvDeviceIdentity = ADVDeviceIdentity` gives no value, so `proto.AdvDeviceIdentity.decode()` type-checks nowhere while `encodeProto('AdvDeviceIdentity', …)` works at runtime). Pick one table and make the namespace install the runtime alias where the `.d.ts` promises one, or drop the aliases from the `.d.ts`.
